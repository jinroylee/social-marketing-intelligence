# Ticket 07: coordinate competing workers without duplicate effects

Status: implemented locally; ticket remains claimed for integration verification.

## Installed behavior and public interfaces

- `OfflineTaskWorker.run_one(task_id, automation_actor)` claims one task-specific PostgreSQL session advisory lock without waiting. Competing workers return the current view without dispatch, a second attempt or a recovery entry. The claim transaction locks the task row and rechecks terminal state before changing ownership; terminal retries preserve the original history/outcome. UUID spellings normalize before claim and publication identities, covering canonical, uppercase and compact forms.
- Public `TaskExecution.transaction(phase)` validates the fresh execution ID and nonterminal task under its row lock and yields the **same ownership connection** for actual effects. `IngestionRunner.resume(..., transaction=...)` joins this scope for all evidence/checkpoints/usage, reconciliation, issues/quarantine, canonical mapping and run completion. Source/canonical mutations accept caller-owned connections. `KnowledgePublications.publish` and `unpublished` accept that connection too, including source-policy locks and legacy content-identity updates. Task checkpoint/prepared-support/completion writes use the same connection. No database transaction spans collector I/O or normalization.
- Session loss releases the claim and aborts the pending transaction. A stale worker cannot reopen a new connection to commit late evidence, canonical facts, publication membership or task state. It raises `TaskExecutionLost`; the CLI reports `task_execution_lost` without a traceback. Ownership is checked before each collector dispatch as well as before accepting its result. Surviving workers clean uncommitted retained files after checking whether the observation actually committed, preserving payloads after a lost commit acknowledgment.
- A successor retains the one original attempt/run, exact campaign or saved human-approval scope, initial worker producer, committed coverage and prepared support. It discovers an existing request-bound publication before reselecting and preserves that publication's actual producer. Real worker-process death after evidence/publication commits resumes without original source payload files, and after publication without the manifest.
- `AcquisitionTasks.read` exposes source-free `execution` metadata: latest execution ID/owner and queued, running, recoverable, waiting or completed state. Running is based on the exact PostgreSQL ownership lock, not a stale persisted status. Local task detail renders execution separately from committed progress. Attempts preserve total `recovery_count`, most recent 20 recovery actors and most recent 100 phases, retaining initial producer and exact prepared support. Migration preserves existing task/approval/attempt/run identities and bounds legacy arrays.
- Trusted `OfflineTaskWorker(..., on_execution=callback)` exposes its `TaskExecution.disconnect()` handle for local operational/controlled connection failure. `before_commit=callback` receives a source-free effect phase inside the owner transaction. These are composition ports, never task/form scope. Both commit-observer and progress-observer exceptions propagate as recoverable interruptions. Closing a session cannot cancel an external call already in flight; its returned result cannot commit locally.
- Different tasks progress independently, including identical canonical identities. A deliberately synchronized test lets distinct tasks both prepare identical capture support before either publication: each retains its own legitimate task/run/publication. Per-task fencing does not claim cross-task novelty admission or semantic deduplication.

## Limits and following tickets

- There is no lease expiry or automatic takeover of a paused connected worker. Handoff follows session closure/process death, or PostgreSQL detecting a network disconnect. Database/transport configuration determines detection latency. Workers do not share a workspace lock or broker.
- The protocol fences local committed effects. It cannot undo/cancel an already dispatched external operation or promise provider-side exactly-once requests/charges. Only simulated fixture I/O is enabled. Safe pending checkpoint replay still depends on the adapter contract; ambiguous paid work still requires route-specific reconciliation. Notifications, monetary attribution/admission and delayed charge reconciliation remain tickets 08–11.
- Crashing the process during a retained-file write can leave an orphan for ingestion's existing reconciliation operation. A surviving worker cleans a rolled-back evidence file without deleting committed payloads. Exact source policy remains with ingestion/publication; historical outcomes do not grant perpetual value visibility.
- Task-local deduplication covers the same task/attempt/run and request-bound publication. Different tasks can intentionally collect the same capture and both prepare it before either publishes; no global capture/semantic novelty guarantee is claimed. The synchronized distinct-task test records this limit explicitly.
- Ticket 08 should create one durable event from the exact task outcome/attempt/run/publication frontier and retain these ownership boundaries. Later accounting/admission must join the actual effect/dispatch protocol rather than checking a claim and committing on a separate connection. Original approved scope, completion meanings and human/automation authorship stay distinct.
