# Ticket 05: approve an exact assistant enrichment proposal

Status: implemented locally; ticket remains claimed for integration verification.

## Installed behavior and public interfaces

- `smi_tasks.TaskAuthority` is trusted composition-time configuration, defaulting to no campaign submitters or human approvers. `campaign_humans`, `campaign_automations` and `proposal_approvers` assign specific identity/kind roles; `for_human(actor_id)` configures the named local CLI/HTTP human. `submit_campaign` checks this authority before campaign admission. An assistant cannot bypass proposal approval by simply calling the campaign operation as an arbitrary automation actor or labeling itself human. A separately configured campaign service can still submit legitimate future campaign coverage work. Configuration and actor construction remain trusted local application boundaries, not hosted authentication.
- `EnrichmentProposal(purpose, intent, subject_ids=(), search_queries=())` / `from_document` validate a supplied refresh/fill/expansion proposal and reject authority/extra JSON fields. `AcquisitionTasks.save_proposal(..., request_id=...)` commits an immutable identifiable revision without submitting work. Its digest pins workspace, purpose/intent, subject/search scope, exact fixture references, route/configuration, manifest path/hash and resource limits. New scope requires a new revision and approval; no conversation/model generation was added.
- `read_proposal(id, actor)` reopens exact scope, limits, proposer/time, human approval and resulting task; `list_proposals(actor)` returns at most 100 newest workspace summaries. Subject/query lists are limited to 30 unique nonempty values of at most 500 characters each; purpose is at most 1000 characters. Existing hard task limits remain in force.
- `approve_proposal(id, human_actor, scope_digest=..., request_id=...)` records the configured human's explicit action, exact revision/digest, workspace and time. Automation, unconfigured principals, submitted human labels, generated approval text and foreign workspaces cannot grant approval. One proposal has at most one approval.
- `submit_approved(id, actor, approval_id=..., scope_digest=..., request_id=...)` reads the exact stored approval and submits only saved scope/limits with server-established assistant origin. Missing/foreign approval, a changed digest, a different/broader proposal or changed manifest is rejected before acknowledgment or dispatch. The submitter and human approver remain separately attributable. On-demand subject/search scope needs no scheduled-keyword membership.
- One approval has at most one logical task. Concurrent identical request-ID retries return the original logical result. Changed payload/actor under that identity conflicts; an alternative request ID for an already approved proposal or submitted approval is explicitly rejected. No unbound duplicate alias identity is acknowledged. The approval read exposes the original request identity so an approved but not yet submitted HTTP action can resume safely after restart.
- Migration adds `enrichment_proposals` and `enrichment_approvals`, plus a unique approval foreign key and explicit campaign/assistant origin-basis constraint on tasks. Campaign and brief remain required for campaign tasks and absent for assistant tasks. Existing campaign-only rows and their IDs/scopes survive repeated migration. The fixture-only worker executes both admitted origins through the same bounded runner/publication path.
- CLI: `save-proposal FILE --request-id ID --offline-manifest PATH [--actor NAME]`, `inspect-proposal ID`, `approve-proposal ID --scope-digest DIGEST --request-id ID --actor HUMAN --approve-exact-scope`, and `submit-approved-task ID --approval-id ID --scope-digest DIGEST --request-id ID [--actor NAME]`. Save/submit use named automation; approval uses the operator's explicit human action. Existing campaign CLI composes only its configured human role. These operator commands must not be exposed as unrestricted assistant tools.
- HTTP: **Proposals** links `GET /proposals`, `GET /proposals/new`, `POST /proposals`, `GET /proposals/ID`, and `POST /proposals/ID/approve`. Review visibly states workspace, immutable revision, purpose/intent, subject/search and exact input scope, route digest and limits. Only the server's named human and an explicit checked review action can approve the displayed digest. Extra origin/actor/approval/scope fields, stale digest, forged CSRF and foreign Origin fail. Approval then task acknowledgment are separately durable and retry-safe; task and proposal pages reopen exact human attribution and each other's links without route configuration. All rendered data is escaped.

The fixture route executes its fully displayed supplied references; subject/search fields record approved intent and do not claim semantic filtering or external search. This route has no live source/model/paid I/O.
- Task recovery/partial publication, competing-worker claims, notifications and monetary admission remain tickets 06–10. - Local named identities and server configuration are trusted in-process boundaries. Hosted authentication and sandboxing arbitrary Python/CLI operator access are not implemented. An assistant integration must receive only its public proposal/approved-submission capabilities, not operator configuration or human approval/campaign commands.
- Technical tests establish neither marketer usefulness nor human language quality, complete market coverage or live route readiness.
