# Acquisition tasks

[`smi_tasks`](../src/smi_tasks/__init__.py) owns durable admission and outcomes for configured schedule, campaign and exactly approved assistant submissions through explicit synthetic offline capabilities and one separately gated live on-demand keyword route. Existing campaigns, ingestion evidence and knowledge publication retain their owners. Tasks are distinct from ingestion runs and publications: accepting work does not fetch, and fetching alone does not establish usable knowledge.

## Submission and authority

`AcquisitionTasks(db, workspace_id="local", route=OfflineRoute(...), authority=TaskAuthority(...))` accepts trusted operator configuration. Authority defaults to no campaign submitters, human approvers or schedule operators/services. `TaskAuthority.for_human(actor_id)` assigns campaign submission and proposal approval to the named local human; `campaign_automations=frozenset({...})` separately configures specific campaign service principals. A generic automation actor, an assistant identity or a client-supplied human label grants neither role. Keep this configuration at the application composition boundary, outside assistant/model/form control. These are trusted local identities, not hosted authentication. `OfflineRoute(manifest_path, version="offline-fixture-v1", limits=RunLimits(max_requests=10, max_pages=10, max_records=10))` permits `fixture-json` supplied references or `offline-keyword-json` query discovery, always with `synthetic: true`. `capability()` reports the configured route, query support/method and an explicit unavailable reason for supplied-reference collection. Request/page/record limits are positive integers at most 100 and bytes at most 10 MiB; the default byte limit is 1 MiB. The configured manifest is at most 1 MiB. The supplied-reference route has at most 100 input items; an empty item list is a completed empty input. The keyword corpus has its separate bounds below. The one live query route below requires separate runtime gates; models remain unavailable through this task path.

`submit_campaign(campaign_id, actor, brief_id=..., purpose=..., request_id=...)` reopens an existing workspace-owned campaign and admits only its current exact brief. The trusted caller constructs `ActorContext`; both its kind and identity must have the configured campaign role. The operation establishes `origin="campaign"` itself. The acknowledgment commits the task ID, workspace, initiating human/automation actor, campaign/brief/version, purpose, unverified input references, route/configuration version, manifest digest, request identity, resource limits, one-attempt limit and queued status. It reads configuration, without reading payloads or executing the collector. Purpose or source/model text cannot select another origin or approve assistant work.

The campaign owner validates and share-locks that exact current brief through `CampaignStore.require_current_brief` in the admission transaction. A concurrent revision waits until the acknowledgment commits; the task owner reads no campaign tables directly.

A workspace/request identity binds that complete scope and initiator. Identical concurrent retries return one task; changed scope, configuration, limits or actor conflicts. A successful retry can reopen the original acknowledgment after the campaign has a successor brief. New submissions against the old brief fail. The queued task retains its original authorized scope. An unconfigured route, foreign workspace or unsupported route cannot dispatch work.

## Supplied proposal and exact approval

`EnrichmentProposal(purpose, intent, subject_ids=(), search_queries=())` supplies an explicit `refresh`, `fill` or `expansion` intent and at least one subject or search query. Each list has at most 30 unique nonempty values, each at most 500 characters; purpose is at most 1000 characters. `from_document` parses these JSON fields and rejects authority/extra fields. `save_proposal(proposal, actor, request_id=...)` saves one immutable identifiable revision. A changed proposal requires a fresh revision ID and fresh approval. Saving grants no acquisition authority and submits no task.

The saved scope includes workspace, purpose/intent, subject/search scope, the configured fixture route/version, exact supplied references, manifest digest, and resource limits. `read_proposal(id, actor)` reopens that scope, its digest, actual proposer, creation time and optional human approval/task; `list_proposals(actor)` returns at most 100 recent revision summaries. The digest pins the entire executable configuration as well as the stated intent. The `fixture-json` route executes its listed supplied references; descriptive subject/search metadata grants no query-discovery capability or semantic relevance. Explicit discovery time fields on this route fail with `keyword_discovery_unavailable_supplied_reference_route`. No conversation or model generation is installed.

`approve_proposal(id, human_actor, scope_digest=..., request_id=...)` is the explicit human action. It requires both human kind and an operator-configured approver identity and records exact revision/digest, workspace, actual human and time. Saved assistant text, a generated `approved` statement, actor kind alone and a supplied origin cannot create approval. Approval does not execute acquisition.

`submit_approved(id, actor, approval_id=..., scope_digest=..., request_id=...)` requires the actual stored approval for that exact workspace/revision/digest. It submits only the saved scope and limits, establishes assistant origin itself, and retains the actual submitter separately from the human approver. A replaced manifest fails before acknowledgment; the worker checks again before collection. Current route configuration cannot broaden the saved scope. Explicit on-demand subjects/queries need no scheduled-keyword membership; registered schedule authority remains separate and is described below.

Concurrent identical request-ID retries return the same proposal, approval or task. A changed payload under that identity conflicts. One proposal has at most one approval, and one approval has at most one logical task. Reusing an already approved proposal or submitted approval with a different request ID is explicitly rejected with `approval_request_conflict` / `task_request_conflict`; retain the original request identity for retries. Approval reads expose that identity so a human can finish an approved but not yet submitted action after restart. An approved task's scope, approver and attribution remain historical even when the server is reopened with different operator configuration.

## Bounded worker and outcomes

`OfflineTaskWorker(db, evidence_root, workspace_id="local").run_one(task_id, automation_actor)` executes or resumes one admitted task. It commits the attempt ID, initial worker actor, ingestion run ID and collecting phase before collection. Recovery keeps the same attempt/run and original authorized scope/limits. Attempts expose a total `recovery_count`, the most recent 20 recovery actors in `resumed_by`, and the most recent 100 phase entries. The initial producer and exact prepared support remain intact when history is bounded. The registry contains only the saved synthetic supplied-reference or keyword capability. The worker and runner verify the saved manifest digest before collection; a prepared publication or committed publication can finish without reopening the input files.

The runner commits each observation with its collection checkpoint, then commits canonical mapping separately. Public `IngestionRunner.resume(run_id, on_commit=...)` reports `evidence_committed` and `canonical_committed` with the observation ID; `inspect(run_id)` reads committed counts without advancing the run. The task worker persists those phases/counts, then saves the exact ordered observation/derivation/assertion/metric selection before publication. Recovery processes retained pending evidence, reuses applied mappings and publishes the saved selection rather than collecting or selecting it again. An interrupted non-retained payload that cannot be replayed fails explicitly; recovery does not refetch it.

Task progress distinguishes collecting, evidence commit, canonical commit, publication preparation, publication commit, waiting and completion. `on_progress=callback` at trusted worker composition receives source-free task snapshots after these owner commits. Callback exceptions propagate as interruptions, retaining committed effects. The publication callback runs before the task completion acknowledgment. Publication and its task-owned `acquisition_task_publications` receipt commit together on the fenced execution session. The later terminal outcome and completion event retain that receipt.

`AcquisitionTasks.read_committed_publication(task_id, actor, connection=None)` reopens a request-bound publication only when its receipt belongs to the task, its exact ordered membership matches the durable prepared support, and `IngestedEvidence.require_run_support` validates that support against the attempt's run. It uses source-free membership/producer/coverage from `KnowledgePublications.find_request`, including after policy withdrawal. Task reads use this same validation to show publication-committed progress after a lost acknowledgment. Recovery checks it before unchanged-support filtering and retains original usable/partial outcome, support, producer and publication identity under a different recovery actor. Current availability remains separate from this historical outcome.

Public publication with a `task:TASK_ID` request string cannot create a task receipt, even with the same worker actor and prepared support. Collisions before collection, after preparation or racing publication fail with `publication_request_conflict`, without a task publication link or usable-update claim. A duplicate public publication is never promoted into a worker receipt. Older completed tasks retain their existing links/outcomes. A pre-repair interrupted publication with no atomic task receipt cannot establish task ownership and fails safely; request text alone cannot repair that ambiguity.

Coverage reports requested inputs, collected/applied/quarantined observations, remaining inputs, eligible/unchanged/unpublished/published members, request/byte use, unresolved identities, missing fields and sanitized issue codes. Remaining inputs count uncollected, pending and quarantined records; identity-free applied input is separately ineligible. A successful subset can publish even when another input fails or a bound stops collection. Unpublished support remains outside current-KB queries. Publication validates current process permission and derivation health again, so withdrawal after preparation fails at publication with no usable-update claim.

| Outcome | Meaning in this slice |
| --- | --- |
| `usable_update` | At least one newly usable exact selection committed, with no reported execution failure. This establishes neither complete market coverage nor business value. |
| `partial_update` | A valid selection committed while collection, limits or mapping left a failed/incomplete remainder. The publication, original failed phase/code and actual coverage are retained. |
| `no_usable_update` | Empty eligible input, no supported fields/metrics, or all eligible support is already published and currently usable, with no execution failure. No new publication or market-absence claim is created. |
| `failure` | No newly usable subset could be committed because collection, limits, normalization, policy or publication failed. Phase/code and actual counts remain visible. |

`KnowledgePublications.unpublished` compares currently usable committed publications using source-owned capture/mapping/selection identities. Equal bytes, provenance, capture/source-as-of times, mapper/policy methods and selected logical fields/metrics are unchanged even when a new run produces new UUIDs. A later capture or mapping is distinct; publication/ingestion time alone establishes no new benefit. Current process permission and derivation health apply to both inputs. This is capture identity comparison, not semantic deduplication or a freshness judgment.

`read(task_id, actor)` survives restart and returns immutable scope/attribution, durable progress and exact support/publication metadata without copying source text or payloads. `list(actor)` returns at most 100 newest workspace tasks. Publication details and `KnowledgeQueries` reopen values under current permissions with explicit synthetic visibility. Terminal retries reopen the same outcome without additional collection.

### Simulated waiting and recovery limits

A trusted `collector=...` worker port can simulate fixture I/O; it still occupies only the saved synthetic collector slot and grants no live-route or admission authority. `CollectedBatch` can return no observations, an opaque next checkpoint, actual `request_attempts` and `waiting="provider_pending"` or `"provider_operation_ambiguous"`. Ingestion atomically saves the checkpoint, wait reason and usage. `provider_pending` is an adapter promise that checkpoint replay safely resumes an existing operation; it must not start another paid operation. Ambiguous operations remain waiting with `resumable=false`; repeated worker execution makes no collector call. Exhausted bounds stop pending work before another call. Task metadata exposes the reason/resumability without exposing the opaque operation handle. No real provider is enabled, and ambiguous-operation reconciliation is future route-specific work.

## Bounded offline keyword discovery

Configure `OfflineRoute` with an `offline-keyword-json` manifest to enable one deterministic synthetic query capability. `EnrichmentProposal` adds optional `published_from` and `published_before` fields. Discovery requires exactly one nonempty `search_queries` value, 1–30 exact subject IDs, and timezone-aware inclusive-from/exclusive-before timestamps spanning at most 366 days. It never derives a query from purpose prose. Existing supplied-reference proposals omit the new fields and preserve their legacy digest shape. Campaign forms without an explicit search/time scope link to the proposal journey; they cannot relabel a purpose or profile reference as discovery. Automatic campaign discovery is composed from saved coverage as described in [the coverage contract](campaigns.md#automatic-coverage-and-discovery); registered scheduled discovery uses the same exact scope below.

The manifest pins `response_path` and its exact lowercase SHA-256 `response_sha256`, plus existing provider/format/policy fields. The fixture search corpus is local, at most 1 MiB and 100 source-shaped records. Its `records` use `account`/`video` source fields, explicit `subjects`, original `captured_at`, optional `source_as_of` and `reference`; see [the example manifest](../examples/synthetic/keyword-discovery-manifest.json), [response](../examples/synthetic/keyword-discovery-response.json) and [proposal](../examples/synthetic/keyword-discovery-proposal.json). Admission reads configuration only. Corpus processing simulates the source's search: every whitespace-separated query term must occur as a case-insensitive literal caption substring, any requested subject must match exactly, and `video.published_at` must fall inside the window. Results follow source response order, with one selected record per simulated page/request. An empty valid response consumes one simulated request. The independent corpus cap bounds fixture lookup; task request/page/record/returned-byte bounds limit the resulting pages. No real provider or network is used.

The saved proposal digest binds scope, configuration and hard limits; a discovery execution digest additionally pins the exact executable task configuration. Submission and the worker revalidate configured capability/limits and immutable digests before new dispatch. Replaced response bytes fail with `discovery_response_changed`. Trusted source I/O injection, task-session fencing, cost admission and normal ingestion/publication remain the existing public boundaries. Bind `UsageAccounting.configure_route('offline-keyword-json', scope_id, operator, max_units='1')` to use the shared configured synthetic meter, including empty pages. No price is inferred. Lost dispatch/settlement retains its unknown liability and cannot be reissued.

Each permitted source member carries exact query, subject/window, route/configuration, corpus digest, source/selection positions, matching/unassessable/corpus counts and `priority='source_response_order'` / `method='literal-caption-subject-time-v1'` in source-owned coverage. Native identities stay in the stable `offline-keyword:public` namespace across queries. Capture/source times and missing source fields stay distinct from local ingestion/publication times. Task coverage reports `scope='bounded_query_discovery'`, one requested query, actual returned observations/requests/bytes and missing fields; `remaining_inputs` counts quarantined/pending records plus one unresolved selection frontier when bounded work stops. It does not estimate the number of market records still missing.

Valid nonmatches are excluded. Missing/invalid caption, subject or publication-time selection fields are unassessable source records; they enter ordinary retained evidence/quarantine and produce sanitized `discovery_selection_unassessable` issues. A valid subset publishes as `partial_update`; entirely invalid input fails. Current process policy can prevent ingestion/publication, and current display policy governs source-owned lineage reads. Empty eligible selection and unchanged previously published captures produce `no_usable_update` without a new publication. Query wording/position alone creates no new capture identity or publication benefit. Recovery reuses committed source support, exact prepared membership and receipted publications even after fixture files disappear; it never refreshes capture dates or turns withdrawal into a false historical failure. Every result retains `market_coverage='unknown'`; complete bounded fixture selection is not market completeness.

Run the browser with `smi-review --offline-manifest examples/synthetic/keyword-discovery-manifest.json --offline-route-version offline-keyword-v1`, save/review/approve the explicit scope, then execute its task with the existing bounded worker command. The CLI `save-proposal` accepts the same example proposal and configured manifest. Neither form nor proposal accepts route, actor, origin, approval or cost configuration. Provider fallback and supplemental acquisition are outside this capability. Registered offline schedules compose it as described below.

## Capture-based discovery avoidance

`OfflineRoute(..., discovery_policy=DiscoveryPolicy(max_capture_age_seconds=86400, processing_revision="canonical-v1"))` opts the offline keyword route into avoidance. The example age is operator configuration, not a product freshness promise. Ages must be integer seconds from 1 through 366 days; the nonempty processing revision is at most 100 characters. Without a policy, fresh repeats keep their bounded retrieval behavior and record `freshness_policy_unconfigured`. Newly admitted discovery scopes pin the policy and response/provider/format context alongside the existing immutable selection/configuration digest. Historical scopes are unchanged; a changed proposal/configuration needs fresh admission and exact approval where applicable. Forms cannot supply policy or processing versions.

`smi_tasks.discovery.DiscoveryHistory` owns a per-task decision before source dispatch. It compares the exact literal query, ordered subjects and publication window, manifest/input digest and provider/format, route version, hard limits, actual mapper key and canonical processing revision. Current governed source/publication operations verify the prior exact support. A successful `usable_update` **or `no_usable_update`** retrieval can support reuse when every retrieved observation has eligible currently usable published support and there was no failed/incomplete remainder. Publication links can refer to earlier authorized work; they confer no task receipt or publication ownership. Upgrade installs history without inventing old decisions: the first post-upgrade retrieval can record already published support for later avoidance.

Every original capture must be known, no later than the trusted worker clock, and at most the configured age. A recent maximum cannot hide another unknown/old capture. Ingestion, processing, publication and skip times never refresh capture dates. Repeated skips refer back to actual retrieval history rather than extending its freshness. Empty results retain unknown capture freshness and remain eligible. Stale, unknown or future captures, changed observations/input/configuration, changed mapper or processing context, failures, partial work, and quota-excluded records remain eligible for bounded retrieval/processing. Raising a scheduled cap can therefore admit an earlier excluded record; a published subset never certifies the complete query as reusable. Canonical processing revisions use `IngestionRunner.resume(..., policy_version=...)` and the existing derivation `policy_version`; they do not relabel mapper software. A new policy revision may create new supported mapping/publication context while preserving the original capture and old result pins.

A fresh skip finishes `no_usable_update` with zero collector calls, request/byte use, new canonical effects, synthetic cost operations, daily post debits and publications. It retains the new task's original approval/campaign/schedule authority and its own attempt/run; prior support is explanatory provenance, never new task publication membership. A prior matching withdrawn source response is withheld with `prior_support_unavailable` and unavailable freshness instead of reconstructing its source copies. Historical publication outcomes remain separate from current usable links and current policy. No cross-provider/namespace merge, fallback, semantic query equivalence or concurrent cross-task retrieval guarantee is inferred.

`AcquisitionTasks.read` exposes `discovery_history`: decision/reason, freshness **at decision**, policy, exact query/retrieval context, actual decision time, prior task/publication links, actual owned publication, recorded usable-publication links plus separately recomputed current `usable_publication_ids`, processing completeness, failure/outcome and capture-basis task. Capture IDs, original times, source identities and metric definitions are reopened through source policy, without copying source values into history. Unavailable captures retain IDs/health while their source context is withheld. The task page labels prior retrieval/publication navigation separately and explicitly states when no new publication was created. Decisions survive restart; committed skips finish without input files, and uncertain cost dispatches still cannot be reissued. Every history mutation joins the existing fenced ownership transaction; no transaction spans source I/O. See [ADR 0013](adr/0013-capture-based-discovery-avoidance.md).

## Registered offline keyword schedule

`ScheduledDiscovery(tasks, clock=...)` in `smi_tasks.schedules` composes the task owner with independently owned schedule tables. `AcquisitionTasks.migrate` installs them after task tables. `configure(document, actor, expected_version=..., live=False)` requires an exact human identity in operator-owned `TaskAuthority.schedule_operators`. `tick(actor)` requires that role or an exact automation identity in `schedule_automations`. `TaskAuthority.for_human` does not grant either role. Actor labels, assistant proposals and HTTP inputs cannot configure these roles or select schedule origin.

The configuration document contains only `timezone` (IANA), `daily_at` (`HH:MM`), `lookback_days` (integer 1–30), `daily_allowance` (integer 1–100000) and `keywords`. There are 0–10 keyword objects, each with a stable `key` (1–64 lowercase ASCII letters/digits/underscore/hyphen, starting with a letter/digit), one nonempty literal `query` (at most 500 characters) and 1–30 distinct explicit `subject_ids` (each at most 500 characters). Keys and trimmed case-insensitive query strings must be distinct in a configuration. Zero keywords pauses future work. These are separate from monitoring investigations/topics. A changed document creates a successor integer version, SHA-256 digest, actual operator and time; stale expected versions fail with `schedule_configuration_conflict`.

The first accounting timezone remains fixed (`schedule_accounting_timezone_fixed` on change). The cadence is `daily-local-v1`, with local-midnight accounting boundaries. Each occurrence records the exact UTC day start/end, local date/timezone, due instant, configuration/digest, allowance version/value and keyword key/query/subjects. During an overlap the earlier due instant wins; a nonexistent local time moves forward by the timezone offset gap. The publication window is half-open from the due local time minus the configured calendar lookback days to the due instant, independent of tick lateness. The trusted injected clock must be aware; ticks reject clock regression. See [the accounting-day decision](adr/0011-stable-schedule-accounting-day.md).

`tick` acknowledges at most ten due current-day occurrences, with unique `(workspace, accounting_day, keyword_key)` across every configuration version. It takes the same workspace lock as configuration edits and commits occurrence dispositions and nested task acknowledgments together. A transient `pending` occurrence exists only inside this transaction; database failure rolls back the entire tick. Source/model collection does not occur in it. `AcquisitionTasks.submit_scheduled(occurrence_id, actor, connection=...)` reopens real schedule-owner authority on that transaction; it accepts no supplied query/origin/configuration context. Tasks retain `origin=schedule`, unique `schedule_occurrence_id`, actual initiator and exact `scope.schedule` authority plus `schedule-offline-v1`, immutable discovery/configuration digests, route and hard limits.

By default, only configured synthetic `offline-keyword-json` routes with process/retention permission are admitted. Explicit live activation is described below. Missing route, supplied-reference capability and policy refusal become retained `refused` occurrences with an explicit reason and no task. A refusal, keyword edit/removal/re-registration or changed daily time cannot generate another occurrence for that same key/day. A distinct key is a new registration, not a new accounting day. Earlier missed dates are not replayed; the tick reports `missed_days_not_replayed` for full intervening dates between observed ticks. Restart retains configurations, occurrences and task identities. `read(actor)` returns current settings, all immutable configuration versions and at most 100 recent occurrences with current task status; `read_occurrence(id, actor)` reopens any exact older identity. Repeated ticks expose existing status in the schedule view without creating another task. Workers execute/resume the task separately through `OfflineTaskWorker.run_one`, preserving normal bounded ingestion/publication, cost admission, no-reissue waiting and exact receipt recovery. Completion uses the existing inbox; monitoring topics and approved on-demand scope remain independent.

The daily new-post allowance is enforced atomically at scheduled canonical ingestion, initially 50 total across all registered keywords and workers. `ScheduledPostAllowance` owns `scheduled_post_days` and `scheduled_post_admissions` within the schedule owner. The runner passes a `CanonicalAdmission` operation to `CanonicalWriter.apply` on the existing fenced execution connection. Normalization and current process-policy validation precede admission; canonical identity locks establish whether content is already known. The day row serializes counts across disjoint identities. Admission, source mapping status and canonical writes commit or roll back together, leaving no separate reservation to leak after failure. Collection and normalization remain outside transactions. Excluded observations retain raw evidence/checkpoints and `skipped` mapping status, with no canonical writes or publication support.

One stable `(platform, namespace, native_id, synthetic)` content identity is a post. A mapped record must identify exactly one content identity to be eligible; a missing/ambiguous identity is skipped as `ineligible_posts`. Malformed or process-denied records retain existing quarantine/failure semantics and consume no new-post admission. First successful admission of previously unknown content increments `new_posts`; already known content records `known_refreshes`, while an identity already admitted/refreshed in this day records `deduplicated_posts`. Both refresh categories may retain legitimate new observations and publish changed permitted support without increasing new-post usage. When used reaches the cap, another unknown identity records `limit_excluded_posts` and is skipped before canonical writes. Empty or entirely limit-excluded input can finish `no_usable_update`; mixed valid subsets retain their ordinary usable/partial outcome. Exclusion is final for that observation; a later configuration does not silently replay it.

Consumption belongs to the occurrence’s recorded workspace/day, even when execution is delayed across midnight. Configuration changes update the current accounting day’s cap/version, preserving used identities and historical day bounds. Increasing the cap opens remaining capacity; decreasing below already used retains that history with remaining zero and prevents further new admissions. Earlier days retain their last applicable cap. Removal/re-registration, new keys and process restart never reset consumption. Older task authority remains immutable, including a historical `allowance_enforcement=not_installed` marker if it predates this installation; the separate `daily_allowance.enforcement` read reports current installed enforcement. Upgrade initializes day metadata from the latest configuration recorded before each fixed day end, without fabricating retrospective debits for canonical effects committed before enforcement. Missing-day bootstrap is serialized with configuration, and cap versions advance monotonically across competing old tasks. See [the atomic admission decision](adr/0012-atomic-scheduled-post-admission.md).

Schedule `read` exposes current-day `daily_allowance`, including zero used and the applicable cap before the first tick of a new day without creating work or consumption; task `read` exposes the exact task day’s current used/remaining/cap/version, aggregate disposition counts and its own `occurrence_counts`. These counts distinguish source observations, unique new posts, known refreshes and exclusions. The HTTP schedule and task views render them alongside independent hard limits and honest fewer-record outcomes. There is no promised fill, market completeness, per-keyword yield or measured throughput. Request/page/record/byte limits and monetary admission remain independent; a skipped result may still consume a real simulated request, record or cost unit.

Use `smi-review --schedule-operator --offline-manifest examples/synthetic/keyword-discovery-manifest.json --offline-route-version offline-keyword-v1` for the explicit local operator surface at `/schedules`. The default server is read-only for schedule configuration/ticks. POST settings/tick retain Host/Origin/CSRF protections and reject forged authority fields; GET never admits or executes. The default is visibly offline. The operator must explicitly select live execution and save its exact route authority as described below; no daemon or external scheduler is configured.

## Competing workers and effect ownership

Workers claim a task-specific PostgreSQL session advisory lock without waiting. UUID spelling is normalized before claiming and forming publication identities. The claim transaction locks the task row and rechecks its terminal outcome before recording a fresh execution ID and actual owner. A competing `run_one` returns the current task view without collecting, creating an attempt or recording a recovery. Terminal retries leave the original result unchanged. Different tasks own independent sessions and can progress concurrently, including when they refer to the same canonical account.

`read` exposes source-free `execution` metadata: its latest execution ID/owner and `queued`, `running`, `recoverable`, `waiting` or `completed` state. Running means PostgreSQL still holds that exact task's ownership lock. A disconnected/interrupted nonterminal task becomes recoverable; waiting preserves its safe-resume/ambiguous distinction. Phase status continues describing committed work separately from active ownership. The local detail page and CLI inspection expose both.

The lock's connection also performs every task-dependent mutation. Public `TaskExecution.transaction(phase)` yields that connection after locking the task row and validating the execution ID and nonterminal state. `IngestionRunner.resume(..., transaction=...)` uses this owner scope for evidence/checkpoints/usage, issues/quarantine, canonical application and run completion. Collector I/O and normalization occur outside database transactions; ownership is checked before dispatch and again in the effect transaction. `EvidenceStore` mutation methods and `CanonicalWriter.reconcile_applied` accept caller-owned connections. `KnowledgePublications.publish` and `unpublished` accept the same optional connection, retaining policy/support locks through the caller's commit. A token check followed by writes on a separate connection would leave a stale-write gap and does not satisfy this contract.

Closing the ownership session releases its lock and rolls back its open transaction. The old worker cannot reconnect to commit a late result: subsequent writes raise `TaskExecutionLost`, leaving successor progress intact. A successor claims the same attempt/run and resumes committed checkpoints, exact prepared support or the existing request-bound publication. A lost publication acknowledgment retains the original publication producer and coverage. Uncommitted retained evidence files are cleaned after rollback when the worker survives; process crashes may leave orphan files for ingestion's existing reconciliation operation.

Trusted worker composition can receive `on_execution=callback`, whose `TaskExecution.disconnect()` closes that worker's ownership session, and `before_commit=callback`, which receives the source-free effect phase inside the transaction. These are local operational/diagnostic and controlled-failure ports, unavailable to forms or proposal scope. Observer exceptions propagate as interruptions and roll back the pending transaction. A before-commit observer must not recursively execute its own task while its transaction holds the task row.

This protocol has no lease expiry or automatic takeover of a paused but connected worker. Handoff follows session closure/process death, or PostgreSQL detecting the disconnect; network failure detection follows database/transport configuration. It fences local committed effects, and cannot cancel an already dispatched external operation or guarantee provider-side exactly-once requests/charges. Safe provider replay still requires its adapter promise; ambiguous work remains waiting. Separate tasks can both prepare identical capture support before either publishes, producing separate attributable publications; unchanged-support filtering is not cross-task novelty admission or semantic deduplication. The completion event joins this same fenced terminal transaction. Configured synthetic monetary admission and settlement also join the ownership session, as described below. Recovery preserves the original exact schedule, campaign or human-approved proposal authority. Existing direct ingestion commands retain their independent capabilities; offline task authorization grants none of their live capabilities. See [ADR 0005](adr/0005-task-session-effect-ownership.md).

## Durable completion inbox

`CompletionInbox(db, workspace_id="local")` owns the local source-free completion surface. `list(actor)` returns at most 100 events, newest first by original completion time/identity; `read(event_id, actor)` reopens one exact identity. Both require the actor's configured workspace, and foreign event IDs return `completion_event_not_found`. This is the same trusted local actor boundary as task reads, rather than hosted authentication.

The worker inserts one `task_completion_events` row in `TaskExecution.transaction('completion')`, together with the terminal task outcome and attempt completion. Any exact task/publication receipt already committed atomically with publication and remains intact if terminal acknowledgment is interrupted. `UNIQUE(task_id)` makes repeated delivery and recovery one logical event. A crash before commit rolls back all of these changes; a crash after commit leaves the event readable without a worker acknowledgment. Session loss fences the actual event write along with the outcome. Event storage contains only its identity, task ID and historical completion time. The immutable terminal task remains the outcome/coverage source of truth; no notification snapshot copies source wording or task-purpose text.

Messages distinguish usable, partial, no usable update and failure. They show actual published/remainder counts, sanitized failed phase/code, the task link and exact publication membership. Each read calls `KnowledgePublications.read(..., purpose='display')`, so display denial, expiry, withdrawal and supersession are evaluated by the source/publication owners. Publication links appear only when some pinned support is both available and current. Original published counts and outcome remain historical; current unavailable support is explicit. No retained source text, source URL or cached availability is stored in events. Existing publication/task views retain their separate policy-aware read contracts.
