# Assistant enrichment journey

Own `AssistantEnrichment.context/propose/read/approve/migrate` and the source-free answer-to-proposal claim in this directory. Before changing gap eligibility, exact scope, recovery or approval, read [the journey contract](../../../docs/tasks.md#assistant-knowledge-gap-enrichment) and [ADR 0018](../../../docs/adr/0018-explicit-assistant-gap-scope.md).

Compose `KnowledgeAssistant`, `AcquisitionTasks` and `CompletionInbox` through their public operations. Write only `assistant_enrichment_requests` here; the parent owns proposal/approval/task SQL, and notifications owns completion lookup. Keep `smi_assistant` independent of task authority. Migrate after campaign, knowledge and task prerequisites; the public migration installs the answer/task prerequisites and its own schema.

Require the original question's exact human requester and workspace for journey actions. Empty published support, a successful missing/ambiguous selection, stale captures or current support loss can justify a visible gap. Model/configuration/accounting failures and generic absent attributes alone grant no gap. Human scope supplies one exact query, subjects and bounded publication window; the generated purpose contains only a fixed gap code. Interpret refresh/fill/expansion as research intent, never a promise the route supplies a missing attribute.

Persist the claim and fresh server-owned nested proposal request before saving through the parent. Retry identical scope/actor/synthetic context; changed bodies conflict. Recover an already committed proposal with `AcquisitionTasks.find_proposal` before reopening route files; retain original configuration/digest. Approval belongs to `AcquisitionTasks.approve_proposal` with its configured actual human and original request identity; submission reuses that exact approval. No model/source/form field can grant authority, change origin or broaden approved scope. This owner performs no acquisition/model I/O and holds no transaction across other owner operations.

Read completion by exact task through `CompletionInbox.read_task`, including events beyond the bounded inbox list. Preserve historical answer membership and outcome while the owners recheck current source permission; later explicit questions alone can see new publications. Verify via public operations and protected loopback HTTP with real PostgreSQL and simulated external I/O. Fault-only DDL may interrupt linkage commits; outcome assertions use the public owners.
