## Durable collection progress

`IngestionRunner.resume(run_id, on_commit=...)` exposes evidence/canonical commit notifications; `inspect(run_id)` reads counts without I/O or state advancement. `CollectedBatch` supports a no-observation wait with an opaque checkpoint and actual request attempts. Pending waits promise safe checkpoint resume; ambiguous operations remain blocked without reissuing collection. The saved checkpoint, waiting reason and request usage commit together. The [task worker](tasks.md) exercises this contract with simulated fixture I/O and the explicitly gated keyword route below. Live route behavior is verified locally with simulated HTTP; actual source operation remains separately authorized.

## Bounded live TikTok keyword discovery

Installed software supports `brightdata-tiktok-keyword`: one explicitly approved on-demand query, one provider, TikTok only, and at most **one returned post**. It uses fixed Bright Data TikTok Posts dataset `gd_lu702nij2f790tmv9h`, `POST /datasets/v3/scrape?type=discover_new&discover_by=keyword&format=json&include_errors=true`, Bearer auth and `{input:[{search_keyword:QUERY,num_of_posts:1}],limit_per_input:1}`. Primary documentation was verified **2026-10-23**: [individual schema](https://docs.brightdata.com/scrapers/gd_lu702nij2f790tmv9h.json), [sync request/status/bounds](https://docs.brightdata.com/api-reference/scrapers/synchronous-requests.md), [async parameters](https://docs.brightdata.com/api-reference/rest-api/scraper/asynchronous-requests.md), [progress](https://docs.brightdata.com/api-reference/scrapers/management-apis/monitor-progress.md), [download](https://docs.brightdata.com/api-reference/scrapers/delivery-apis/download-snapshot.md), [billing/schema distinctions](https://docs.brightdata.com/products/scrapers/scrapers-library/faqs.md). There is no live receipt for this route.

A 200 supplies bounded JSON records. A 202 after the documented 60-second sync wait supplies an opaque snapshot handle; the transport has a finite 75-second socket timeout, 8192-byte body ceiling and 65536-byte response ceiling (exact-cap responses reject conservatively). One worker invocation makes at most one HTTP request. Persisted source checkpoints own handle/phase/step/not-before; validated Retry-After seconds govern the next progress request (ten seconds when absent). Ready status permits existing-snapshot download; a documented download 202 (not ready/building) retains that same download phase and its retry delay. Failed/canceled status is a terminal source failure; unknown/mismatched status, malformed/oversized output, HTTP errors or lost responses retain uncertainty without another POST. No redirect, retry, poll loop, rerun, fallback provider or background daemon exists. No-observation response bytes consume the original cumulative run budget.

The keyword schema lists URL/discovery-input output only; normal discovery can continue to full page collection, whose optional full fields are documented separately. URL-only results fail accurately with explicit missing fields. Publication requires valid numeric `post_id`/`profile_id`, consistent HTTPS TikTok URL and any returned username, assessable caption/creation time, local all-term caption and half-open approved-time eligibility, normal canonical rules and current policy. Valid out-of-scope rows count as returned but provide no usable update. Approved subject IDs identify investigation context without asserting a product relationship. Canonical identities use `brightdata:tiktok-posts`; numeric `play_count`, `digg_count`, `comment_count` and `collect_count` retain distinct provider definitions. Handles are never native account IDs; invalid or conflicting rows fail without invented facts.

Original capture and metric measurement timestamps are unknown because the documented schema does not guarantee them; retrieval time is separate metadata. Existing exact query/context history records the actual mapper and processing revision. Unknown captures prevent fresh-retrieval avoidance; unchanged valid responses can still produce an honest no-new-publication result. Historical task receipts and exact prepared support recover before missing source inputs/runtime credentials are needed.

Runtime defaults disable this route. Exact proposal approval does not supply process/server enablement, live-operation authorization, source-use authorization, credential, current policy, persisted provider-basis cost binding or shared ceiling. The review server requires `--enable-live-discovery` before accepting this configured route; it only acknowledges tasks. The separate worker requires `LiveDiscoveryConfig` gates or the explicit `run-live-discovery-task` CLI flags and transient `BRIGHT_DATA_API_TOKEN`. Source policy can independently deny/expire/revoke use. Registered schedules default offline and require [explicit recorded operator activation](tasks.md#recorded-live-keyword-schedule-activation) of this exact route; enabling the process alone grants no schedule authority.

Every HTTP attempt receives one shared configured declared-unit reservation on its task execution transaction before I/O. The scope requires provider `brightdata`, service `tiktok-keyword`, provider-reported basis, unit `declared-record-bound`, explicit rates/period/currency and ceiling. Rates and invoice charges are never defaulted. Delivered-record counts do not prove final charges; all source attempts retain dispatched commitments and awaiting-final-measurement state. Explicit provider-basis final reconciliation can settle exact liabilities, including final zero evidence, without restoring missing responses or granting dispatch. The result cap is not a verified commercial charge cap; billing lag and zero-overshoot guarantee remain unknown. [ADR 0014](adr/0014-live-discovery-response-and-billing-identity.md) records this trade-off.

All implementation verification uses simulated HTTP and isolated local PostgreSQL. Actual credential, source-use clearance, operation authorization, current commercial bounds/rates and bounded live receipt remain **unmet external runtime prerequisites**. Software tests do not establish service readiness, market completeness, language quality or marketer usefulness.

## Profile-only nickname supplementation

The installed optional task extension uses the existing TikTok Profiles dataset `gd_l1villgoiiidt09ci` once for one exact human-approved profile URL/native ID after primary keyword evidence corroborates the target. Primary docs verified **2026-10-27**: [profile schema](https://docs.brightdata.com/scrapers/gd_l1villgoiiidt09ci.json) supplies `id`, `account_id`, `url` and `nickname`; [synchronous API](https://docs.brightdata.com/api-reference/scrapers/synchronous-requests.md) documents one-input requests, output-field filtering and 200/202 semantics. Historical profile receipts do not establish current keyword readiness, source-use permission or billing.

`BrightDataTransport.fetch_profile_field` requests only `id|account_id|url|nickname` in an object body's `custom_output_fields`, one URL input and `limit_per_input=1`, using fixed-host Bearer HTTPS and the parent's strict remaining response-byte cap. It never invokes the posts dataset. `BrightDataProfileFieldCollector` retains the actual source response and retrieval time; `BrightDataNicknameMapper` verifies exact URL/stable native identity and maps only `nickname` under `tiktok:public`, without metrics. Provider output filtering is requested, not assumed infallible. Original capture/source-as-of times stay unknown. Source-specific identities and existing primary metric definitions remain separate; account equivalence is unestablished.

The optional task-owned policy, exact approval, runtime profile authorization, shared deferred cost binding and original run limits govern this operation; see [the complete task contract](tasks.md#one-missing-profile-nickname). A 202 response stops as pending/unresumed without polling. Invalid identity/schema, byte-bound response, HTTP failure or transport ambiguity stops without fallback/reissue and retains unknown final billing. The oEmbed adapter remains reference-only and is not a retained profile capability. No actual supplementary source receipt or marketer-quality validation is claimed.

## Gated official X recent search

Installed software supports `x-recent-search`: fixed-host Bearer-authenticated `GET https://api.x.com/2/tweets/search/recent`, one literal-phrase query, explicit start/end, `max_results=10`, `sort_order=recency`, `post.fields=created_at,public_metrics` and no expansions. The **2026-10-28** [endpoint/OpenAPI reference](https://docs.x.com/x-api/posts/search-recent-posts) names `post.fields`; its [quickstart](https://docs.x.com/x-api/posts/search/quickstart/recent-search) still demonstrates `tweet.fields`. The current reference is selected, and actual acceptance remains an unverified live prerequisite. These are dated contract observations rather than a current provider acceptance check; the retained primary captures are indexed below.

The dated [rate-limit reference](https://docs.x.com/x-api/fundamentals/rate-limits) states 450 app requests per 15 minutes, 10–100 results and 512 ordinary-query characters; the endpoint/OpenAPI schema separately allows 4096. The software chooses a smaller local bound rather than treating that discrepancy as extra authority. The installed route uses one ten-record page and a smaller 200-character literal query plus a 2048-byte encoded-URL cap; the whole start time must remain within seven days. It waits at least 30 seconds after a cadence boundary. `data`/`meta.result_count`, numeric native IDs and bounded text/public metrics are validated. Current `repost_count`, `like_count` and `reply_count` map directly; the legacy `retweet_count` name is not substituted, and `impression_count` is not relabeled as the distinct unsupported `view_count`. An empty `meta.result_count=0` is valid; missing source fields remain unknown. `next_token` marks uncollected pagination and is never retained or followed. Pending status, HTTP/redirect/transport error, malformed data, exact-cap/oversized bytes, extra records and elapsed-deadline failures retain uncertainty without another request. See [all operational bounds](monitoring.md#gated-periodic-live-recent-x).

The dated [pricing page](https://docs.x.com/x-api/getting-started/pricing) describes resource-based Post reads, configured credit/spending controls and soft per-UTC-day deduplication. The software does not install a commercial rate, assume repeated resources are free or infer a final invoice from returned posts. Shared declared commitments and explicit final provider reconciliation follow [the cost contract](costs.md#official-x-recent-search-commitments).

The [Developer Policy](https://docs.x.com/developer-terms/policy) imposes permitted-use, display, redistribution and current-state/deletion obligations, including applicable prompt removal within 24 hours of notice. Its X-performance benchmarking restrictions do not establish permission for this product's intended market-analysis use. Technical access alone proves neither licensing nor display/storage clearance. No automatic provider compliance feed or current-display refresh is installed. An operator must establish applicable authorization/compliance before enabling the route; the source policy remains an independent current gate. Existing withdrawal/retention propagates to selected published copies. No live receipt, actual charges, service readiness or permission approval is claimed.

## Shared model transport contract

The installed bounded route uses OpenAI Responses. The **2026-10-20** read-only primary-contract review selected the [create reference](https://developers.openai.com/api/reference/resources/responses/methods/create), [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) and [token-counting](https://developers.openai.com/api/docs/guides/token-counting) guides. This is a dated contract basis, not current account access, live execution or pricing evidence.

The route sends one HTTPS POST with bearer authentication, strict schema under `text.format`, explicit `store=false`, finite request/response/output bounds, no tools and no automatic retry. All object fields are required with explicit nullable optional values and no extra properties. Refusal, incomplete output and missing usage remain separate outcomes. Input/output/total/cache/reasoning usage is validated; generated output includes reasoning/formatting, and local character counts are not exact full-request tokens. No hidden live token-count request is issued. Exact supported model/input/context/output contracts and explicit rates/weights remain trusted configuration; [campaign interpretation](campaigns.md#bounded-natural-language-interpretation) and [accounting](costs.md#responses-token-measurement-and-provider-provenance) own those details. Schema validity cannot grant authority, weaken human criteria or establish semantic truth/usefulness.
