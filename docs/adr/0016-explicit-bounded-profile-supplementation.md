# Bind supplementary profile reads to exact parent authority

Status: accepted

A keyword query and a mutable discovered handle cannot authorize arbitrary profile retrieval. The supported nickname fill therefore requires an exact human-approved profile URL and expected stable native ID, corroborated by the primary result, plus an operator-pinned value policy. Its single profile-only operation shares the parent's ingestion run, original remaining limits and explicitly shared declared spending allowance. This deliberately forgoes automatic handle expansion, route fallback and profile-to-post transitions.

A matching native number establishes this acquisition's target scope; it does not establish account equivalence between `brightdata:tiktok-posts` and `tiktok:public`. Profile nickname support retains its own observation, unknown original capture time and provenance. Current KB support and source permissions constrain dispatch after recovery as well as initial selection. Durable stopping decisions preserve useful primary publication when further retrieval lacks value, permission, capability or budget. Pending, failed and lost supplementary responses retain their cost liability and receive no automatic poll or paid retry; final billing reconciliation cannot recover missing source evidence. See [the implemented contract](../tasks.md#one-missing-profile-nickname).
